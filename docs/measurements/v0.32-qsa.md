# 0.32 sparse attention (QSA) against dense

**Status: working, experimental, slower than dense.** Sparse QSA runs on 4× B70 with the vLLM Triton kernels, answers
correctly, passes the gates below, and holds the long-context needles. It is 0.74–0.81× dense on prefill and
one-stream decode and 0.46–0.53× at 4–8 concurrent streams. Use the dense release
([v0.32/README.md](../../v0.32/README.md)) when throughput matters; use this variant to run the checkpoint as it was
trained (indexer kept, 2,048-token selection budget), or to work on the kernels.

Setup: Qwen3.8-Flash-Next W4A16, Intel AutoRound @ `4c67bf68`, the serving shape of
[`v0.32/engines/qsa-serve.args`](../../v0.32/engines/qsa-serve.args) and
[`qsa-serve.env`](../../v0.32/engines/qsa-serve.env) (DFlash2 K=7, async scheduling, 8 sequences, 4096-token prefill
chunks, GPU memory fraction 0.89, patched oneCCL plugin, 128 GiB CPU KV tier), vLLM v0.32.0 + the dense series
([`patches/vllm/`](../../v0.32/patches/vllm/)) + the QSA add-on ([`patches/vllm-qsa/`](../../v0.32/patches/vllm-qsa/),
26 patches). Sparse engine: `B70_QSA_ATTN_IMPL=attn2`, `B70_QSA_TOPK=native_det`. 4× Arc Pro B70, compute-runtime
26.35, Triton 3.8.0+xpu, torch 2.14.0+xpu.

## 1. End to end, same harness as the dense results

The harness and the dense column are the ones behind [v0.32/README.md §Numbers](../../v0.32/README.md#numbers): greedy
decode (400 tokens), 4 concurrent requests, 8 streams × 2K-token prompts, uncached single-stream prefill, one engine at
a time on an idle host. The dense column is the configuration with the patched plugin (`serve-plugin.env`); the sparse
engine runs the same configuration plus the two QSA keys. Single runs; differences under ~5 % are noise.

| | dense | **sparse QSA** | sparse / dense |
|---|---|---|---|
| decode, 1 stream (tok/s) | 169.3 | **125.0** | 0.74 |
| decode, 4 concurrent (total tok/s) | 306.2 | **161.2** | 0.53 |
| decode, 8 streams (total tok/s, 2 repeats) | 605.5 | **281.4 / 279.7** | 0.46 |
| prefill 8K (tok/s) | 6,304.6 | **5,095.7** | 0.81 |
| prefill 32K (tok/s) | 6,113.6 | **4,634.5** | 0.76 |
| prefill 131K (tok/s; time to first token) | 4,640.9 (28.1 s) | **3,456.4 (37.8 s)** | 0.74 |
| decode, 1 stream at 32K depth, 512 tokens (tok/s, 2 repeats) | 181.2 / 193.4 | **150.1 / 145.9** | 0.80 |
| GPU KV cache (tokens) | 397,309 | **329,287** | 0.83 |
| boot to first real completion | ~4 min | ~5 min (more on a cold Triton cache) | |

Gates on the sparse engine: needle retrieval at 32K (depth 50 %) and 128K (depth 10 % and 90 %) 3/3; five-question
sanity set (thinking off, temperature 0) 5/5; burst gate 0 bad in 150 requests; structured output with speculative
decoding clean. No crash, no device error, no traceback in the runs reported here.

Reading:

1. **Where the time goes.** Prefill and one-stream decode lose about a quarter against dense. Multi-stream decode loses
   about half: the indexer scorer and the top-k grow with rows × context, and the attention kernel is no longer the
   dominant term. These splits are inferred from per-kernel timings, not measured inside the engine; an in-engine
   profile has not been done.
2. **Against the first working sparse build** (kernels untuned, torch top-k; the same harness): prefill 1,807 / 1,593 /
   1,076 tok/s at 8K / 32K / 131K, one-stream decode 119.4, four streams 143.7, eight streams 188.0 / 197.5, KV
   302,144 tokens. The kernel work below is what moved it to the table above.
3. **Capturing the sparse body into graphs** (`B70_QSA_EAGER_BREAK=0`) works and passed the same gates, but it was no
   faster at 1, 4 or 8 streams and cost 25.7K KV tokens (303,572 against 329,287), so the series keeps the eager break.
4. **Open levers**, in the order we expect them to pay: one top-k per verify step reused across the 7 draft rows; a
   histogram top-k so `native_det` stops falling back to a full-width torch sort at the full page-table width; making
   the tuned scorer configurations the defaults (the sweeps measured the decode scorer 2.1–3.5× faster than the defaults
   this engine runs); an incremental indexer-key cache; the QSA side caches' share of KV; 262K prefill (see §3).

## 2. Fidelity against dense

Dense is a comparison arm here, not an oracle: the checkpoint was trained with sparse attention. Sparse selects every
token up to 2,051, so the two should agree up to that length. The fidelity runs used
the torch top-k (`B70_QSA_TOPK=torch`), the reference; the selector-identity test shows `native_det` returning the
torch selector's output on every case and launch (§4). Each engine ran alone, idle, at equal concurrency.

**Prompts under 2K tokens** (8 prompts × 256 tokens, c=1 and c=8; token-level comparison with logged ids, then a
teacher-forced pass over the dense engine's stream, 2,048 positions):

| pair | KL mean | p95 | max | top-1 agreement |
|---|---|---|---|---|
| dense vs dense (one run against another) | 0.00115 | 0.00615 | 0.058 | 99.17 % |
| dense vs sparse | **0.00115** | 0.00547 | 0.044 | 99.32 % |
| sparse vs sparse | 0.00117 | 0.00663 | 0.052 | 99.07 % |

Under 2K tokens sparse is indistinguishable from dense: the divergence equals each engine's own run-to-run spread.
Greedy token streams diverge at near-ties in 8/8 prompts for dense vs sparse; dense against itself diverges at
near-ties in 6/8 (c=1) and 7/8 (c=8). That is the same kind of divergence, not a failure.

**A 12,288-token English technical document, teacher-forced, `prompt_logprobs` 5, identical token ids on both engines,
two runs of each** (KL in nats, top-1 agreement; the "floor" is one engine against its own second run):

| position | dense floor | sparse floor | **dense vs sparse** | p99 KL, dense vs sparse |
|---|---|---|---|---|
| 1–512 | 0.0000 / 100 % | 0.0000 / 100 % | 0.0078 / 93.7 % | 0.060 |
| 512–2,048 | 0.0088 / 96.4 % | 0.0093 / 95.8 % | 0.0100 / 95.6 % | 0.090 |
| 2,048–4,096 | 0.0101 / 95.5 % | 0.0096 / 95.7 % | 0.0112 / 95.8 % | 0.097 |
| 4,096–8,192 | 0.0132 / 94.3 % | 0.0134 / 94.1 % | 0.0204 / 93.2 % | 0.170 |
| 8,192–12,288 | 0.0150 / 94.2 % | 0.0168 / 94.1 % | 0.0308 / 91.0 % | 0.267 |
| **≤ 2K** | 0.0066 / 97.3 % | 0.0070 / 96.8 % | **0.0094 / 95.2 %** | 0.083 |
| **> 2K** | 0.0133 / 94.5 % | 0.0140 / 94.4 % | **0.0227 / 92.8 %** | 0.206 |

1. Up to 2K, dense against sparse is 1.4× the engines' own floor. In the first 512 tokens each engine repeats itself
   exactly, but the two differ (KL 0.0078): a fixed numerical difference between the QSA path (fused prepare, its own
   attention kernel) and dense flash attention. It is not selection, which keeps every token there.
2. Beyond 2K the gap is 1.7× the floor, growing with depth to about 2× at 8–12K (top-1 91.0 % against 94.1 %). That is
   the divergence sparse selection should produce. No outliers: the largest p99 is 0.27 nats. Whether the difference
   helps or hurts on long-context tasks is not measured here; no task-level comparison has been run.
3. **Both engines are nondeterministic from about token 512** (the floor is exactly 0 up to 512 and positive after).
   That sits in the shared stack and is not QSA's. It also means bit-level comparison gates fail on either line.

This used one document and one text type; it is a first number, not a quality evaluation.

## 3. Kernel level (labelled: not end to end)

One B70, tensor-parallel-4 shapes (6 query heads per KV head, head dim 256), microseconds per layer call, XPU-graph
replay for decode, a 4,096-row chunk for prefill, page-table width 65,728. Every row was checked against a torch
reference. `splitk` is the first Triton kernel (its default configuration and a swept one); `attn2` is the new
register-spill-free kernel in this series (`B70_QSA_ATTN_IMPL=attn2`, 0 spills; tile 32 × 8 chunks, 256 GRF, one warp).
"SYCL" is the SYCL QSA kernel of analytics-zoo/vllm-xpu-kernels (PR #22, branch `downstream/v0.31.0` @ `f597f304`), built
as a bar on the same card (FP16; limited to 256,000 tokens of context).

Decode attention:

| rows | context | splitk default | splitk swept | **attn2** | SYCL |
|---|---|---|---|---|---|
| 8 | 4K | 454 | 155.5 | **54.7** | 53 |
| 8 | 131K | 470 | 169.4 | **57.3** | 56 |
| 8 | 262K | 471 | 170.6 | **58.0** | n/a (above 256,000) |
| 32 | 4K | 1,910 | 489.8 | **97.5** | 173 |
| 32 | 131K | 2,810 | 613.9 | **205.2** | 222 |
| 64 | 4K | 4,363 | 1,032.9 | **212.3** | 362 |
| 64 | 131K | 5,598 | 1,200.3 | **377.8** | 432 |

Prefill attention, 4,096-row chunk:

| context | splitk default | splitk swept | **attn2** | SYCL |
|---|---|---|---|---|
| 8K | n/a | 51,457 | **9,753** | n/a |
| 32K | 122,269 | 53,633 | **10,244** | n/a |
| 131K | 147,600 | 58,718 | **13,161** | 22,148 |
| 262K | 163,571 | 63,495 | **17,640** | n/a (above 256,000) |

1. `attn2` matches the SYCL kernel at 8 rows and is below it at 32 and 64 rows; on prefill it is below it at 131K.
2. A build of Intel's Triton backend from main (3.9.0+gitf552c356) gave `attn2` nothing (within ±2 %). It speeds the
   old kernel's prefill a lot (13.4 ms at 32K); at 262K that old kernel on Intel main (15.6 ms) is faster than `attn2`
   on 3.8.0 (17.6 ms). The release runs Triton 3.8.0.
3. The kernel numbers do not transfer one-to-one to the engine: the engine ratio in §1 is set by the whole step, and the
   selection (scorer and top-k) is where the multi-stream cost is.
4. The scorer and top-k kernels were swept too (decode scorer 2.1–3.5×, prefill scorer 11× over their defaults); those
   winners are **not** applied in the engine run of §1.

## 5. What this does not show

- No multi-day run of the sparse variant; it has served for hours.
- No task-level quality comparison with dense (long-context retrieval beyond three needles, agent tasks).
- No in-engine profile; the cost split in §1 is inferred.
- Only the Intel AutoRound weights, only the patched-plugin configuration, one host.
- 262K prefill and the fp8 KV paths are not tuned or tested.
- The sweep and engine-definition scripts used to drive the measurements run on our own host and are not in the kit.
