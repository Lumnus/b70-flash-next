## 3. Host memory under the CPU KV tier (2026-10-03)

At 128 GiB of CPU KV, both builds stopped on our 8 GiB host-RAM guard under a replay of 6 real agent sessions. The
cause: vllm-xpu-kernels stages every CPU→GPU KV load through a pinned buffer the size of the load, and torch keeps
pinned blocks ≤ 1 GiB in its host cache for good. Two fixes, both measured over two back-to-back 6-session replays:

| | staging (before) | 0031 (`B70_OFFLOAD_H2D_DIRECT=1`) | kernels 0.1.14.1+b70.3 (`B70_OFFLOAD_H2D_DIRECT=0`) |
|---|---|---|---|
| xe host memory per rank | +2.56 GiB | +0.06 GiB | **+0.058 GiB, once, then flat** |
| CPU→GPU load bandwidth | 8–12 GB/s | 19.8 GB/s | 19.6–19.9 GB/s |
| guard stops | yes | none | none |
| prefix reuse | 94.4 % | 94.4 % | 94.4 % |
| errors | — | 0 | 0 |

The kernel fix is what we serve; 0031 stays in the series, gated off, as the fallback for stock kernels.

Prefix reuse is ~96 % in real use and 94.4 % in the replay. How it splits between the GPU pool (~311K tokens) and the
CPU tier depends on the workload: with 6 sessions in flight the GPU tier serves 46–55 % of prompt tokens and the CPU
tier the rest; with 3 sessions the GPU tier serves 91 %.
